# Pulso setup and implementation status

From `apps/web`, run `npm ci`, `npm test`, and `npm run dev` (or `npm run build`). The three visible role screens currently still use **local example data** and are not connected to the new backend. The sign-in form does not authenticate; don't enter credentials or use these screens for real student data. The local instructor deadline form does not yet save to Convex. No syllabus import exists.

## Convex foundation

`convex/schema.ts` and the `accounts`, `sections`, `assessments`, `student`, and `admin` modules provide the first server-side implementation. They use verified Google identity and allow only `0000-0000@lspu.edu.ph` (four digits, hyphen, four digits) accounts. Sign-in does **not** grant access by itself: an enabled account must be provisioned by an administrator. Role, ownership, and enrollment checks are enforced by the queries and mutations. An instructor can manage only their assigned sections; a student sees only enrolled sections; department heatmaps are admin-only and suppress cohorts with fewer than five active students. Heatmap counts and collision checks are aggregates, not individual student lists. Deadlines are manually created, edited, and deleted and appear in the enrolled student's timeline.

Configure a Convex development deployment using `npx convex dev`. Create an OAuth 2.0 Google client for the university app and configure its approved browser origins in Google Cloud. In the Convex deployment environment, set `AUTH_GOOGLE_CLIENT_ID` to that client ID. Set `PULSO_BOOTSTRAP_ADMIN_EMAIL` to the **verified** university email of the first administrator; it must follow the format above. `accounts.bootstrapAdmin` can be called once, only by that authenticated identity. Then an administrator can provision accounts, assign instructors to sections, and enroll students using the server APIs. Remove the bootstrap email setting after successful setup. Never put secrets or actual user data in source control.

**Important:** there is currently no Google sign-in/token flow in the frontend and no administrator UI to perform these calls. The bootstrap function cannot be called from an unauthenticated Convex dashboard session: the first admin must call it with a valid Google ID token through an authenticated Convex client. Google client configuration and a Convex deployment must exist before end-to-end verification. The `auth.config.ts` issuer and audience must match the Google client issuing those ID tokens. Domain-format checking is not a substitute for university account governance; ensure the organization controls account issuance and revocation. The app currently has no automatic synchronization with Google account status.

This is a foundation, **not production-ready**: wire Google sign-in and the screens to Convex, build secure administrator provisioning/management, test with real Google identity and deployment configuration, establish privacy/retention policies and review scalability, then replace the demo gate before using personal data. The study-assistant action, strict validation, fallback and UI in the updated plan are not yet implemented. Previous sample tables are retained in the schema only to avoid destroying existing demo data; they are not accessed by the new APIs. Migrate or remove them deliberately before a production rollout. No unauthenticated sample seed/query functions are deployed in this version.

The revised source plan is `docs/project-plan.md`. It is a target plan, not a statement that all features have already been implemented.
